# 功能需求 — 优惠券发放与核销中心

需求基线来源：`../plan/req-plan.md`（Q-001 ~ Q-015、D-01 ~ D-20）。
角色缩写：OP=运营人员，US=普通用户，VE=核销人员，AD=管理员。

## 术语与不变量

以下三条不变量贯穿全部功能需求，任何实现不得破坏。

- **INV-1 库存守恒**：`total_stock = claimed_count + 剩余库存`，且 `claimed_count` 单调递增，永不回退。
- **INV-2 券的完全划分**：`claimed_count = 已核销 + 未核销未过期 + 未核销已过期`。
- **INV-3 状态两态**：`user_coupon.status` 只有 `UNUSED` / `USED`。"已过期"不是存储状态，是 `expires_at <= now()` 的实时判断。

## 一、活动管理

### FR-001 创建优惠券活动

- **描述**：运营创建一个优惠券活动，定义面额、库存、时间窗、每用户限领数与品类。
- **角色**：OP
- **前置条件**：已登录且角色为 OP。
- **业务规则**：
  - 字段：`name`、`category`、`face_value`、`total_stock`、`start_at`、`end_at`、`validity_minutes`、`per_user_limit`
  - `category` 为枚举（餐饮/出行/购物/生活服务），来源 D-07，用于 AI 推荐生成理由
  - `validity_minutes` 为"领取后有效时长"，单位分钟，来源 D-16
  - `per_user_limit` 默认 1，来源 D-02
  - `total_stock >= 1`、`face_value > 0`、`end_at > start_at`、`validity_minutes >= 1`、`per_user_limit >= 1`
  - `claimed_count` 初始化为 0，**创建时不预生成任何券记录**（D-01）
  - 时间字段以 UTC 存储（D-16）
- **正常结果**：活动创建成功，返回活动 ID 与完整字段。
- **异常处理**：字段校验失败返回 400 并指明字段；非 OP 角色返回 403（FR-061）。
- **优先级**：P0
- **来源**：初始需求 3.1；D-02、D-07、D-16
- **验收标准**：
  - AC-1 传入合法字段创建成功，`claimed_count = 0`，且 `user_coupon` 表新增行数为 0
  - AC-2 `total_stock = 0` 或 `end_at <= start_at` 时返回 400
  - AC-3 不传 `per_user_limit` 时落库值为 1
  - AC-4 US/VE/AD 角色调用返回 403

### FR-002 编辑优惠券活动

- **描述**：运营修改活动的可变字段。
- **角色**：OP
- **前置条件**：活动存在。
- **业务规则**：
  - 可改：`name`、`category`、`end_at`、`per_user_limit`、`total_stock`（**仅允许调高**）
  - 不可改：`face_value`、`start_at`（活动已开始后）、`validity_minutes`（已领出的券其 `expires_at` 已落库，改它会造成同一活动内规则不一致）
  - `total_stock` 只增不减：调低会使 `claimed_count > total_stock`，直接破坏 INV-1
- **正常结果**：更新成功，返回更新后的活动。
- **异常处理**：试图调低 `total_stock` 返回 400 并说明原因；改不可变字段返回 400。
- **优先级**：P1
- **来源**：初始需求 3.1；INV-1
- **验收标准**：
  - AC-1 将 `total_stock` 由 100 改为 50 返回 400
  - AC-2 将 `total_stock` 由 100 改为 200 成功，剩余库存随之增加
  - AC-3 修改 `face_value` 返回 400

### FR-003 活动列表与详情查询

- **描述**：按角色查询活动。
- **角色**：OP（全部字段与统计）、US（仅可领取的活动）、AD（全部 + 统计）
- **业务规则**：
  - **活动状态不落库**，由时间实时派生：`now < start_at` → 未开始；`start_at <= now <= end_at` → 进行中；`now > end_at` → 已结束（与 INV-3 的惰性原则一致）
  - US 视图只返回：进行中、且 `claimed_count < total_stock`、且该用户未达 `per_user_limit` 的活动
  - 支持分页
- **正常结果**：返回活动列表，含派生状态与剩余库存。
- **异常处理**：无权限字段不下发给 US（不返回风控与统计字段）。
- **优先级**：P0
- **来源**：初始需求 3.1、3.4
- **验收标准**：
  - AC-1 `end_at` 已过的活动在 US 视图中不出现
  - AC-2 库存耗尽的活动在 US 视图中不出现
  - AC-3 派生状态与 `now()` 一致，无需任何后台任务参与

## 二、领券

### FR-010 用户领取优惠券（库存原子扣减）

- **描述**：用户领取指定活动的一张券，库存原子扣减，不可超发。
- **角色**：US
- **前置条件**：已登录；活动处于进行中；已通过 FR-012 风控评估。
- **业务规则**（顺序即实现顺序）：
  1. 风控前置（FR-012），决策为拦截或人工审核时**直接终止，不进入事务**
  2. 开启事务
  3. 条件扣减库存：`UPDATE campaign SET claimed_count = claimed_count + 1 WHERE id = :cid AND claimed_count < total_stock`；受影响行数为 0 → 回滚，返回"库存不足"
  4. 计算 `seq = 该用户在本活动已领数 + 1`；`seq > per_user_limit` → 回滚，返回"已达领取上限"
  5. 生成券码（FR-014）
  6. 计算 `expires_at = min(campaign.end_at, now() + validity_minutes)`（D-16）
  7. 插入 `user_coupon(campaign_id, user_id, seq, code, status='UNUSED', expires_at)`，受 `UNIQUE(campaign_id, user_id, seq)` 约束；唯一冲突 → 回滚，返回"已达领取上限"
  8. 提交
- **正常结果**：返回券码、面额、`expires_at`、活动信息。
- **异常处理**：
  - 库存不足 → 409「库存不足」
  - 超过限领 → 409「已达领取上限」（`per_user_limit=1` 时即初始需求验收点 4.2 的"已领取"场景，D-02）
  - 活动未开始/已结束 → 409
  - 风控拦截 → 403「操作过于频繁，已被风控拦截」
  - 风控人工审核 → 403「账号存在异常，需人工审核」
- **优先级**：P0
- **来源**：初始需求 3.2、4.1、4.2；D-01、D-02、D-03、D-16
- **验收标准**：
  - AC-1 库存为 N，**N+1 个不同用户**并发领取，恰好 N 个成功、1 个失败且失败原因为"库存不足"；事后 `claimed_count = N` 且 `user_coupon` 行数 = N（SC-001、NFR-001、D-08 的压测约束）
  - AC-2 `per_user_limit = 1` 时同一用户第二次领取返回"已达领取上限"，且 `claimed_count` 未增加
  - AC-3 `per_user_limit = 3` 时同一用户可成功领 3 次，第 4 次失败
  - AC-4 任一失败路径均不产生 `user_coupon` 行、不改变 `claimed_count`
  - AC-5 领券接口的调用链中**不存在任何 Bedrock 调用**，除非风控落入灰区（D-05、D-08）

### FR-011 我的优惠券列表

- **描述**：用户查看自己的券及其真实可用状态。
- **角色**：US
- **业务规则**：返回券码、面额、活动名、`expires_at`，以及**派生展示状态**：`USED` → 已核销；`UNUSED` 且 `expires_at > now()` → 可用；`UNUSED` 且 `expires_at <= now()` → 已过期（INV-3）。
- **正常结果**：仅返回本人券，支持按状态筛选。
- **异常处理**：查询他人券一律返回本人数据集，不越权（NFR-004）。
- **优先级**：P0
- **来源**：初始需求 二、3.3
- **验收标准**：
  - AC-1 券在 `expires_at` 到达后，无需任何后台任务，列表状态即变为"已过期"
  - AC-2 用户 A 无法在响应中看到用户 B 的任何券

### FR-014 券码生成

- **描述**：为每张券生成不可预测的短码。
- **角色**：系统
- **业务规则**：
  - 10 位 Crockford Base32，剔除易混淆字符 `0`/`O`、`1`/`I`/`L`
  - 使用密码学安全随机源
  - 全表唯一索引；冲突则重新生成，最多重试 5 次
  - **禁止自增或任何可推导编码**：核销仅凭券码（FR-020），可预测编码等价于他人券可被批量枚举核销
- **正常结果**：返回唯一券码。
- **异常处理**：连续 5 次冲突则整笔领取失败并回滚（概率可忽略，但不得静默降级为可预测码）。
- **优先级**：P0
- **来源**：D-19；NFR-006
- **验收标准**：
  - AC-1 生成 10000 个券码，无重复、无 `0O1IL` 字符
  - AC-2 券码不含活动 ID、用户 ID、时间戳等可推导信息

## 三、核销

### FR-020 核销优惠券（幂等）

- **描述**：核销人员凭券码核销一张券，重复请求返回一致结果。
- **角色**：VE
- **前置条件**：已登录且角色为 VE。
- **业务规则**：
  1. 单条条件 UPDATE 即完成全部并发控制：
     `UPDATE user_coupon SET status='USED', used_at=now(), used_by=:vid WHERE code=:code AND status='UNUSED' AND expires_at > now()`
  2. 受影响行数 = 1 → 核销成功
  3. 受影响行数 = 0 → 回查该券，**按 `status` 优先、时间其次**判定原因（终态优先，D-04）：
     - `status='USED'` → 「已核销」（即使该券此刻也已过期）
     - `status='UNUSED'` 且 `expires_at <= now()` → 「券已过期」
     - 查不到 → 「券不存在」
  - **幂等键即券码本身**，不引入 `Idempotency-Key`（D-04）
  - 券的归属用户不参与核销校验；用户仅负责出示券码（D-12）
- **正常结果**：返回核销成功、券面额、`used_at`、核销人。
- **异常处理**：已核销 → 409「已核销」；已过期 → 409「券已过期」；不存在 → 404「券不存在」；非 VE 角色 → 403。
- **优先级**：P0
- **来源**：初始需求 3.3、4.3、4.4；D-04、D-12
- **验收标准**：
  - AC-1 首次核销成功；**再次核销返回"已核销"**，且响应体与第二、三、四次完全一致（SC-004）
  - AC-2 `validity_minutes = 1` 的券，领取后等待超过 1 分钟再核销，返回"券已过期"，全程未修改数据库（SC-003、D-16）
  - AC-3 一张**已核销**的券在过期之后再核销，返回"已核销"而非"券已过期"
  - AC-4 同一券码并发 20 次核销，恰好 1 次成功、19 次返回"已核销"，`used_at` 与 `used_by` 只被写入一次
  - AC-5 US/OP/AD 角色调用核销接口返回 403

### FR-021 核销前查验券

- **描述**：核销人员在执行核销前查询券的当前状态。
- **角色**：VE
- **业务规则**：只读，返回券面额、活动名、派生状态、归属用户标识（脱敏）。查询本身不改变任何状态。
- **正常结果**：返回券信息与是否可核销的判定。
- **异常处理**：券不存在返回 404。
- **优先级**：P1
- **来源**：初始需求 二（核销人员职责）
- **验收标准**：
  - AC-1 连续查询 10 次，券状态不发生任何变化
  - AC-2 对已过期券返回"不可核销：券已过期"，与 FR-020 的判定口径一致

## 四、统计与监控

### FR-030 活动统计面板

- **描述**：展示活动的领取率、核销率、剩余库存。
- **角色**：AD、OP
- **业务规则**（口径固定，来源 D-10）：
  - 领取率 = `claimed_count / total_stock`。**系统无曝光埋点，分母只能是库存**，面板必须显式标注该口径，避免按电商直觉误读
  - 核销率 = `已核销数 / claimed_count`（分母取已领取数；若取库存总量，低领取率活动的核销率将永远趋近 0 且与领取率信息重复）
  - 剩余库存 = `total_stock - claimed_count`
  - 补充展示券的完全划分：已核销 / 未核销未过期 / 未核销已过期（INV-2）
  - **实时 SQL 聚合**，不建预聚合表（D-10）
  - `claimed_count = 0` 时核销率显示为「—」而非 0 或除零错误
- **正常结果**：返回单活动指标与全局汇总。
- **异常处理**：活动不存在返回 404；非 AD/OP 返回 403。
- **优先级**：P0
- **来源**：初始需求 3.4；D-10
- **验收标准**：
  - AC-1 面板数字与直接 SQL 查询结果完全一致（无中间缓存层）
  - AC-2 `total_stock = claimed_count + 剩余库存` 在任意时刻成立（INV-1）
  - AC-3 `claimed_count = 已核销 + 未核销未过期 + 未核销已过期` 在任意时刻成立（INV-2）
  - AC-4 领取率分母口径在界面上有文字说明
  - AC-5 新建活动（`claimed_count = 0`）时核销率不报错

### FR-031 异常监控指标

- **描述**：面板展示风控相关的异常指标，落地初始需求二"管理员：查看统计、监控异常"。
- **角色**：AD
- **业务规则**：
  - 近 24 小时风控拦截次数（`risk_event` 中决策为拦截的计数）
  - 待处理风险标记数（`risk_event` 中状态为待处理的计数）
  - 初始需求 3.4 未列出这两项，但需求二赋予管理员"监控异常"职责却无任何对应指标，本需求补齐该缺口（D-11）
- **正常结果**：返回两个计数及最近拦截记录列表。
- **异常处理**：非 AD 返回 403。
- **优先级**：P1
- **来源**：初始需求 二；D-11
- **验收标准**：
  - AC-1 执行 SC-006（10 秒 50 次领取）后，拦截计数在面板上当场增加，且增量等于被拦截的请求数
  - AC-2 拦截计数只统计近 24 小时

## 五、AI 智能推券

### FR-040 个性化推荐（确定性召回 + AI 重排）

- **描述**：为用户生成个性化优惠券推荐列表与推荐理由。
- **角色**：US
- **前置条件**：已登录。**独立接口，不在领券路径上**（D-05）。
- **业务规则**：
  1. **确定性召回**：SQL 查出候选集 = 进行中 + `claimed_count < total_stock` + 该用户未达 `per_user_limit` 的活动
  2. 构造用户特征：历史领取次数、历史核销次数、核销率、偏好 `category` 分布、偏好面额区间。**本系统无订单与支付数据，用户历史行为仅来自领券与核销记录**
  3. 调用 Bedrock Converse（FR-042），要求返回候选 ID 的排序子集 + 每个 ID 的理由
  4. **返回后逐个校验 ID 在候选白名单内，不在的直接丢弃**（D-06）。AI 只能重排给定集合，不能凭空生成活动
  5. 冷启动（无历史行为）：候选集按热度（领取率）排序作为默认序，prompt 中显式标注"新用户，无历史行为"，理由采用新人话术
  6. 任一环节失败 → FR-041 降级
- **正常结果**：返回非空推荐列表，每项含活动信息 + 理由文本 + 是否降级标识。
- **异常处理**：候选集本身为空（无任何可领活动）时返回空列表并附说明，此为合法状态而非错误。
- **优先级**：P0
- **来源**：初始需求 5、4.5；D-05、D-06、D-07
- **验收标准**：
  - AC-1 存在可领活动时返回非空列表，每项理由文本非空（SC-005）
  - AC-2 AI 返回一个不在候选集内的活动 ID 时，该项被丢弃且不出现在响应中
  - AC-3 已过期、已售罄、该用户已领满的活动永不出现在推荐结果中
  - AC-4 全新用户（零历史）调用仍返回非空列表
  - AC-5 推荐接口的调用不影响任何库存或券状态（纯读）

### FR-041 推荐降级

- **描述**：AI 不可用时，推荐功能降级为规则排序。
- **角色**：系统
- **业务规则**：触发条件为超时、网络失败、凭证失效、HTTP 非 2xx、输出不是合法 JSON、必填字段缺失、ID 全部不在白名单。降级行为为按热度排序候选集 + 模板理由，并在响应中标记 `degraded=true`。**"返回非空列表"由降级路径硬保证，不依赖 AI 可用性。**
- **正常结果**：返回非空推荐列表 + 模板理由。
- **异常处理**：不向用户暴露 AI 错误细节，不泄露凭证信息（NFR-004）。
- **优先级**：P0
- **来源**：初始需求 6（降级要求）；D-15；AIDLC 设计门禁
- **验收标准**：
  - AC-1 将 `AWS_BEARER_TOKEN_BEDROCK` 置为无效值后，推荐接口仍返回非空列表且 `degraded=true`
  - AC-2 断开外网后，推荐接口响应时间不超过配置的超时上限 + 重试次数（3s × 2）
  - AC-3 降级发生时 `ai_invocation` 中留有一条记录，含降级原因（FR-053）
  - AC-4 响应体与日志中不出现凭证任何片段

### FR-042 Bedrock 调用封装

- **描述**：统一封装 Bedrock Converse 调用，供推荐与风控复用。
- **角色**：系统
- **业务规则**：
  - 使用 **Converse API**，模型由 `modelId` 配置项决定，换模型不改代码（D-14）
  - region 固定 `us-east-1`（可配）
  - 凭证仅从环境变量 `AWS_BEARER_TOKEN_BEDROCK` 读取；**当前使用短期 key，有效期 12 小时，过期后替换环境变量并重启即生效**（D-15）
  - **不依赖 Bedrock Structured Outputs 特性**；prompt 内声明 JSON 结构，服务端对返回值无条件严格校验：字段齐全、ID 在白名单内、评分为 0~100 整数（D-14）
  - 超时分级：推荐 3s、最多重试 1 次；风控灰区 2s、不重试（风控挂在交易链路上，宁可降级也不拖延）
  - 每次调用写 `ai_invocation`（FR-053）
- **正常结果**：返回校验通过的结构化对象。
- **异常处理**：任何失败均转换为统一的降级信号，向上层抛出可识别异常，不向用户透传原始错误。
- **优先级**：P0
- **来源**：初始需求 一、5、6；D-14、D-15
- **验收标准**：
  - AC-1 仅修改 `modelId` 配置即可切换模型，无需改动业务代码
  - AC-2 AI 返回非法 JSON 时不抛未捕获异常，转为降级信号
  - AC-3 AI 返回评分 150 时被判为非法并降级
  - AC-4 风控调用实测超时上限不超过 2s

## 六、AI 异常检测与风控

### FR-050 领券风控评估（两层漏斗）

- **描述**：领券前评估用户行为风险，返回评分与决策。
- **角色**：系统（US 触发）
- **前置条件**：位于 FR-010 步骤 1，在事务之外。
- **业务规则**（两层漏斗，D-08）：
  1. **规则层**（纯 DB 计数，毫秒级）：统计该 `user_id` 近 10 秒领取请求数
     - `> hard_threshold`（默认 10）→ 决策 **拦截**，**不调用 Bedrock**
     - 落入 `[gray_low, hard_threshold]`（默认 5~10）→ 进入第 2 步
     - `< gray_low` → 决策 **放行**，不调用 Bedrock
  2. **AI 层**（仅灰区）：同步调用一次 Bedrock（FR-042，2s 超时不重试），返回 0~100 风险评分 + 决策 `放行 / 人工审核`
  3. AI 失败 → FR-051 降级
  - 计数维度为 `user_id`（D-08）
  - `hard_threshold`、`gray_low`、时间窗口均为**配置项**，演示现场可调
  - 三态决策的语义：**放行**继续领券；**拦截**当次失败，静默，不产生运营待办；**人工审核**当次失败，**产生运营待办**（FR-052），用户文案不同
- **正常结果**：返回评分、决策、是否降级、判定依据。
- **异常处理**：规则层查询失败视为放行（不因监控故障阻断业务），但记录告警。
- **优先级**：P0
- **来源**：初始需求 6、4.6；D-08
- **验收标准**：
  - AC-1 同一用户 10 秒内发起 50 次领取，第 11 次起被拦截，返回风控拦截（SC-006）
  - AC-2 该场景下**全程未产生任何 Bedrock 调用**（`ai_invocation` 中无对应记录），因此断网也能完整演示
  - AC-3 正常单次领取（低频）不调用 Bedrock，响应时间不受 AI 影响
  - AC-4 阈值改为 3 后，第 4 次即被拦截，无需改代码
  - AC-5 **N+1 个不同用户**并发领取时无人被风控拦截（验证计数维度为 `user_id`，D-08）

### FR-051 风控降级

- **描述**：AI 不可用时风控降级为规则引擎。
- **角色**：系统
- **业务规则**：灰区调用 AI 失败时，采用规则层保守判定：请求数越接近硬阈值风险越高；达到灰区上限判为人工审核，否则放行。降级不得导致领券整体失败。
- **正常结果**：返回规则评分与决策，标记 `degraded=true`。
- **异常处理**：不向用户暴露 AI 错误。
- **优先级**：P0
- **来源**：初始需求 6（"AI 不可用时降级为规则引擎"）；D-15
- **验收标准**：
  - AC-1 凭证失效状态下，领券功能完全正常，风控仍能拦截高频请求
  - AC-2 断网状态下可完整走通竞赛演示六步（SC-001 ~ SC-006）
  - AC-3 降级在 `ai_invocation` 留痕

### FR-052 风险标记管理

- **描述**：运营审核风控产生的风险标记。
- **角色**：OP
- **业务规则**（D-09，依据初始需求二原文"审核风控标记"）：
  - **审核对象是挂在用户身上的风险标记，不是一笔待批的领取请求**
  - 决策为拦截或人工审核时写入 `risk_event`：`user_id`、触发时间、窗口内请求数、评分、决策、是否降级、关联 `ai_invocation` ID、状态（待处理/已解除/维持限制）
  - 运营处理：**解除** → 该用户风险标记清除，用户可自行重新领取；**维持限制** → 标记保留
  - **被拦截或待审核的请求不占用库存、不创建券、不改变 `claimed_count`**（否则 INV-1 被破坏，且给攻击者以占用库存的拒绝服务手段）
  - 解除后用户走**完全正常的领取路径**，系统不代为补发（领取逻辑永远只有一条路径）
- **正常结果**：标记列表可筛选，处理后状态更新并记录处理人与时间。
- **异常处理**：非 OP 返回 403；重复处理同一标记返回当前状态（幂等）。
- **优先级**：P0
- **来源**：初始需求 二、6；D-09
- **验收标准**：
  - AC-1 风控拦截发生后，运营后台风险标记列表出现对应记录
  - AC-2 列表中每条记录可查看 AI 评分与判定理由（依赖 FR-053，无理由则运营无从审核）
  - AC-3 拦截或待审核发生前后 `claimed_count` 与 `user_coupon` 行数均无变化
  - AC-4 解除标记后该用户可成功领取
  - AC-5 US/VE/AD 调用该接口返回 403

### FR-053 AI 调用留痕

- **描述**：每次 AI 调用（含降级）落库留痕。
- **角色**：系统
- **业务规则**：`ai_invocation` 记录：用途（推荐/风控）、`model_id`、prompt 版本号、输入特征快照、原始输出、解析后评分与决策、耗时毫秒、是否降级、降级原因、关联 `user_id`。**不存完整 prompt**（由版本号 + 特征快照可完整重建）。**禁止记录任何凭证片段**。
- **正常结果**：每次调用与每次降级各一条记录。
- **异常处理**：留痕写入失败不得阻断主业务，但需告警。
- **优先级**：P0
- **来源**：D-20；AIDLC 设计门禁（AI 可追溯性）；FR-052 的前置依赖
- **验收标准**：
  - AC-1 一次推荐调用后产生且仅产生一条记录，含耗时与模型 ID
  - AC-2 降级场景产生记录且 `degraded=true`、降级原因非空
  - AC-3 全表检索不出现凭证任何片段（NFR-004）
  - AC-4 通过该表可回答"某个风险标记为何被判为人工审核"

### FR-061 接口级角色权限校验

- **描述**：后端对每个接口声明允许的角色，越权返回 403。
- **角色**：系统
- **业务规则**：权限在**后端**声明并强制，不依赖前端隐藏。核心映射：活动创建/编辑与风险标记处理 → OP；领券与我的券与推荐 → US；核销与查验 → VE；统计面板 → AD（活动统计 OP 亦可读）；异常监控 → AD。
- **正常结果**：授权请求正常执行。
- **异常处理**：越权返回 403 且不泄露资源是否存在。
- **优先级**：P0
- **来源**：初始需求 二；D-13
- **验收标准**：
  - AC-1 US 调用创建活动接口返回 403
  - AC-2 US 调用核销接口返回 403
  - AC-3 VE 调用统计面板接口返回 403
  - AC-4 OP 调用核销接口返回 403
  - AC-5 越权响应体不包含目标资源的任何字段

### FR-062 Mock 用户批量初始化
