### Q-001
[Question]
券的领域建模：采用"活动计数器 + 领取时生成券实例"（A），还是"创建活动时预生成 N 条券记录"（B）？

[Answer]
A。条件 UPDATE 即可保证不超发，无需锁表；大库存活动不会在创建时写入海量行。

### Q-002
[Question]
初始需求 3.1 要求活动可配"每用户限领数"（暗示 >1），验收点 4.2 却要求"同一用户重复领取，第二次返回已领取"（暗示恒为 1）。两者矛盾，以哪个为准？

[Answer]
保留 `per_user_limit`，默认 1，运营可在前端配置；超出时返回"已达领取上限"。验收点 4.2 视为 `per_user_limit = 1` 的特例。
（附带解决 TBD-1：`per_user_limit` 配置权限归**运营人员**，不归管理员。）

### Q-003
[Question]
存储选型与并发原语（同一决策）：PostgreSQL（A）、MySQL 8（B）、SQLite（C）？

[Answer]
A（PostgreSQL）。并发控制全部交由数据库：条件 UPDATE 扣库存 + `UNIQUE(campaign_id, user_id, seq)` 兜个人上限。不引入 Redis。

### Q-004
[Question]
核销的幂等键、过期状态是否落库、是否支持运营作废券？

[Answer]
- 幂等键 = **券码本身**（券状态机），不引入 `Idempotency-Key`
- "已过期"**不落库**，靠 `expires_at` 惰性比较
- **不支持作废券**，`status` 仅 `UNUSED` / `USED` 两态，`claimed_count` 单调递增
- 终态优先：已核销的券过期后再核销，返回"已核销"

### Q-005
[Question]
竞赛演示流程步骤 b 写"用户领取成功（含 AI 推荐理由）"。AI 推荐是否要进入领券接口的同步调用路径？

[Answer]
A —— **AI 不进领券路径**。推荐为独立接口 `GET /api/recommendations`，在用户决策**之前**调用。
依据：领券是全系统唯一有并发正确性要求的接口，挂上外部网络调用会导致（1）响应时间受 Bedrock 支配（2）N+1 并发验收变成 N+1 次并发 Bedrock 调用并触发限流，使"库存不足"与"AI 超时"两类失败无法区分（3）`campaign` 热点行的行锁被持有秒级。

### Q-006
[Question]
推荐的召回集如何约束？活动是否需要语义标签？冷启动如何兜底？

[Answer]
- 召回：A —— 确定性 SQL 召回候选集，**AI 只做重排 + 生成理由**，返回后逐个校验 ID 在候选白名单内，不在的丢弃
- **活动新增 `category` 字段**（对初始需求 3.1 字段清单的扩张）。否则活动属性只有数字与时间，AI 无法生成有实质意义的推荐理由
- 冷启动：按热度排序 + prompt 标注"新用户"；AI 失败/超时/输出不合法则降级为热度排序 + 模板理由，保证推荐列表非空是硬保证

### Q-007
[Question]
初始需求 6 要求"领券时评估风险"（同步阻塞决策），与 Q-005 结论冲突。如何收口？风控阈值与计数维度？

[Answer]
C —— **两层漏斗**：
1. 规则层（纯 DB 计数，毫秒级）命中硬阈值 → 直接拦截，**不调用 Bedrock**
2. 仅灰区流量同步调用一次 AI → 返回评分 + `放行 / 人工审核`
3. AI 失败或超时 → 降级为规则层保守判定

计数维度 = `user_id`。硬阈值 = 10 秒内领取请求 > 10 次；灰区 = 10 秒内 5~10 次；均可配置。
验收点 4.1 的并发压测**必须使用 N+1 个不同用户**（同一用户会被风控拦截，会被误判为库存扣减缺陷）。

### Q-008
[Question]
被判定为"人工审核"的领取请求，当场是否占用库存？

[Answer]
D —— **人工审核的对象是用户身上的风险标记，不是一笔待批的领取**。
依据初始需求二原文："运营人员：创建/管理优惠券活动，**审核风控标记**"。
行为：当次领取直接失败并写入 `risk_event`；运营在后台处理标记；解除后用户自行重新领取。
效果：领取逻辑永远只有一条路径；`claimed_count` 永不回退；不给攻击者"触发灰区判定占用库存"的拒绝服务手段。
约束：运营后台的**风险标记列表页为必做项**，它是三态决策中"人工审核"唯一的可见证据。

### Q-009
[Question]
统计口径：领取率与核销率的分母？实时聚合还是预聚合表？"监控异常"职责如何落地？

[Answer]
- 领取率 = `claimed_count / total_stock`。系统无曝光埋点数据，分母只能是库存，面板须显式标注口径
- 核销率 = `used / claimed_count`
- 剩余库存 = `total_stock - claimed_count`（恒等式，不单独存字段）
- **实时 SQL 聚合**，不做预聚合表（避免双写不一致导致面板与数据库打架）
- 面板补两个异常指标：近 24 小时风控拦截次数、待处理风险标记数

### Q-010
[Question]
核销接口谁能调用（TBD-3）？认证做到什么程度？是否做权限校验验收？

[Answer]
- A —— **核销唯一入口，仅核销人员可执行**。项目已排除支付结算，用户自助核销属纯自毁操作；核销之所以存在是因为线下有人验券
- 认证：预置 Mock 用户 + 简单登录签发 JWT（载荷含 `user_id`、`role`），不做注册/密码策略/找回密码。用户须支持批量 seed
- **越权返回 403 列入验收清单**

### Q-011
[Question]
Bedrock 接入：key 类型、调用方式、结构化输出保障、超时重试、region 与模型？

[Answer]
- 调用方式：**Converse API**（跨模型统一接口，换模型仅改 `modelId`）
- 结构化输出：**不依赖 Structured Outputs 特性**；prompt 要求 JSON + 服务端无条件严格校验（字段齐全、ID 在白名单内、评分落在 0-100）
- 超时：推荐接口 3s / 最多重试 1 次；风控灰区 2s / 不重试
- region：**us-east-1**
- 模型：推荐与风控共用一个轻量模型 + 两套 prompt

### Q-012
[Question]
用户提供的 API Token 经解析为**短期 key**（凭证 ID 以 `ASIA` 开头、带 `X-Amz-Security-Token`、`X-Amz-Expires=43200` 即 12 小时、签发于 2026-07-29T13:47:52Z）。12 小时过期如何安排？

[Answer]
B —— 接受短期 key，纯环境变量注入，**过期就换新的**。
AI 降级路径不再作为可选项讨论：它本就是初始需求 6 明文要求的交付功能（"AI 不可用时降级为规则引擎"），且 AIDLC 设计门禁硬性要求"降级路径 + 可追溯"，因此按**必交付且必须可演示**处理。
安全事项：该 token 曾在对话中明文出现，应视为已泄露并重新生成。凭证仅从环境变量读取，禁止进入仓库、日志、错误响应与演示材料截图。

### Q-013
[Question]
券的有效期语义？初始需求存在死结：若券过期时间 = 活动结束时间，则活动结束后无法领券，**无法在演示现场自然构造一张过期券**。

[Answer]
C —— `expires_at = min(活动结束时间, 领取时间 + 有效时长)`，**领取时计算并落库**。
有效时长单位为**分钟**。所有时间戳存 UTC（`timestamptz`），展示时转本地时区。
收益：建一个"领取后有效 1 分钟"的活动即可现场自然演示"过期券核销"，全程不触碰数据库。
注意区分：`expires_at` 是落库数据；"是否已过期"是惰性判断。

### Q-014
[Question]
技术栈与交付形态？

[Answer]
- 后端：Python + FastAPI + SQLAlchemy + Alembic。boto3 是 Bedrock 文档默认语言；FastAPI 自动生成的 `/docs` 可直接作为演示界面调用接口
- 前端：单个 React SPA（Vite + Tailwind + 成熟组件库）+ 角色路由守卫。**不做 Next.js**（无 SEO/首屏需求，SSR 只增加心智负担与部署单元）。前端是本项目最大成本项
- 部署：`docker compose up` 一键起 db + api + web
- **并发验收脚本作为正式交付物**放入 `scripts/`

### Q-015
[Question]
券码生成规则？AI 调用是否留痕？

[Answer]
- 券码 = **10 位 Crockford Base32**（剔除 `0/O`、`1/I/L`），唯一索引 + 冲突重生成。**否决自增/可预测编码**：核销仅凭券码，可预测编码意味着他人券可被批量枚举核销
- 建 **`ai_invocation`** 表逐次留痕（用途、`model_id`、prompt 版本、输入特征快照、原始输出、评分与决策、耗时、是否降级、降级原因），不存完整 prompt。该表是"人工审核"能真正运转的前提——没有理由，运营无从审核标记
