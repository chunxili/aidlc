## ADR 技术决策记录

### ADR-001 并发控制完全下沉到数据库
- **背景**：库存不超发（INV-1）与每用户限领（FR-010）两个约束落在不同表上，跨表约束的并发正确性取决于数据库的隔离级别与锁原语。
- **决策**：库存用条件 UPDATE（`WHERE claimed_count < total_stock`）；个人上限用 `UNIQUE(campaign_id, user_id, seq)`。二者置于同一事务内，**应用层不实现任何锁、队列或串行化**。唯一冲突触发回滚，库存 `+1` 随事务一并回滚，不产生库存泄漏。
- **理由**：条件 UPDATE 的受影响行数即判定结果，无需 SELECT-then-UPDATE 的竞态窗口；唯一索引把"并发下两个请求算出同一个 seq"这一情形交给数据库拒绝。
- **代价**：单活动领取吞吐上限为 `campaign` 单行的更新速率（所有并发排在同一行的行锁上）。项目无 TPS 指标，已在 NFR-001 中接受。
- **替代方案**：Redis + Lua 原子扣减（被否，单机部署下多一个进程即多一个演示前置故障点，且 Redis 与 DB 的补偿逻辑是本项目性价比最低的复杂度）；悲观锁 `SELECT FOR UPDATE`（被否，等价于串行化但持锁时间更长）。
- 关联：NFR-001、FR-010、INV-1

### ADR-002 过期是时间的函数，不是状态
- **决策**：`user_coupon.status` 仅 `UNUSED` / `USED`；"已过期"由 `expires_at <= now()` 实时判断。活动的"未开始/进行中/已结束"同理由 `start_at` / `end_at` 派生，不落库。
- **理由**：过期若落库，要么引入定时任务扫表（单机部署下多一个调度器，且刷库之前的状态是错的），要么读时惰性回写（写放大）。不落库则任何时刻的查询都绝对准确。
- **代价**：统计 SQL 需写成 `status='UNUSED' AND expires_at <= now()` 这类条件，语句略长。
- 关联：INV-3、ADR-003、FR-003、FR-011、FR-030

### ADR-003 `expires_at` 落库，"是否过期"惰性判断
- **决策**：`expires_at = min(campaign.end_at, claimed_at + validity_minutes)`，在**领取时计算并落库**。
- **理由**：该值依赖领取时刻，无法事后重算；而"是否已过期"是对这个已知值的比较，必须实时。二者一个是数据、一个是判断，容易在实现时混淆，故单列一条 ADR。
- **附带收益**：`validity_minutes` 采用分钟粒度使"过期券核销"（SC-003）可在演示现场自然构造，无需改库或提前一天准备。
- 关联：D-16、FR-010、FR-020、NFR-010

### ADR-004 核销幂等由券的状态机承担
- **决策**：核销为单条条件 UPDATE；`rowcount = 0` 时回查券，**按 `status` 优先、时间其次**判定原因。不引入 `Idempotency-Key` 表。
- **理由**：券天生是单次消费资源，"是否已核销"这一事实存在于券自身。引入外部幂等键会派生"同一张券用两个不同 key 核销算不算重复"这类自找的问题，其答案最终仍要回到券的状态机。
- **终态优先**：已核销的券过期后再核销返回"已核销"。核销已发生且不可撤销；"过期"描述的是未被使用的券失去资格，对已消费的券不成立。返回"券已过期"会误导核销人员认为该券未被使用。
- 关联：NFR-002、FR-020、D-04

### ADR-005 AI 与交易链路解耦
- **决策**：推荐为独立只读接口，**不在领券路径上**；风控采用两层漏斗，规则层命中硬阈值直接拦截且**不调用 Bedrock**，仅灰区同步调用一次 AI。
- **理由**：领券是全系统唯一有并发正确性要求的接口。若挂上外部网络调用：响应时间受 Bedrock 支配；N+1 并发验收会变成 N+1 次并发 Bedrock 调用并触发限流，使"库存不足"与"AI 超时"两类失败无法区分；`campaign` 热点行的行锁被持有秒级。
- **附带收益**：SC-006（10 秒 50 次）由规则层拦截，全程零 Bedrock 调用，断网亦可演示。
- 关联：D-05、D-08、FR-050、NFR-003

### ADR-006 前端选 Ant Design 5，不用 Next.js
- **决策**：React 19 + Vite + TypeScript + Ant Design 5，单 SPA + 角色路由守卫。
- **理由**：前端是本项目最大成本项，需要五类页面（领券、我的券、核销台、活动管理与风险标记、统计面板）。Ant Design 自带 Table/Form/Statistic/Descriptions/Result 等成品组件，可避免手写表格与表单；shadcn/ui 需逐个复制组件并自行组合，前期速度更慢。SSR 在本项目无收益（无 SEO、无首屏指标），只增加"哪些代码跑在服务端"的心智负担与一个 Node 部署单元。
- **代价**：Ant Design 定制主题不如 Tailwind 灵活，产物体积较大。演示项目不受影响。
- 关联：CON-004、D-17

### ADR-007 人工审核的对象是风险标记，不是待批领取
- **决策**：风控判为"人工审核"时当次领取直接失败并写 `risk_event`；运营处理标记；解除后用户自行重领。**不创建 `PENDING_REVIEW` 券、不预占库存。**
- **理由**：依据需求原文"审核风控**标记**"。若预占库存，`claimed_count` 将可减，同时破坏 INV-1 与 INV-3，并使统计口径歧义化（被拒绝的那次算不算领过）；更严重的是给攻击者一个免费的库存占用手段——故意触发灰区判定即可让库存挂在审核中，**风控本身沦为拒绝服务工具**。
- **代价**：被判审核的用户需自行重领，而非被动等券到账。
- 关联：D-09、FR-052

### ADR-008 统计实时聚合，禁止预聚合表
- **决策**：全部指标由实时 SQL 聚合得出，不建汇总表、不加缓存层。
- **理由**：预聚合引入双写，双写必然出现不一致，届时面板数字与数据库打架是演示时最难解释的缺陷。项目数据量为演示级，实时聚合成本可忽略。
- **口径固定**：领取率分母为库存总量（系统无曝光埋点，CON-005）；核销率分母为已领取数。
- 关联：NFR-009、FR-030、INV-1、INV-2

### ADR-009 AI 输出不信任，服务端强校验
- **决策**：不依赖 Bedrock Structured Outputs 特性；prompt 内声明 JSON 结构，服务端对返回值无条件校验（字段齐全、活动 ID 必须落在本次候选白名单内、评分为 0~100 整数），任一不过即降级。
- **理由**：Structured Outputs 的模型与区域可用性无法在设计阶段查证（见 DQ-003），把 FR-040 的验收押在未验证的特性上是赌博；服务端校验是完全自主可控的。白名单校验同时消除"AI 推荐了不存在的活动"这一演示级风险。
- 关联：FR-040、FR-042、D-06、D-14

### ADR-010 券码不可预测
- **决策**：10 位 Crockford Base32（剔除 `0`/`O`、`1`/`I`/`L`），密码学安全随机源，唯一索引 + 冲突重试。
- **理由**：核销仅凭券码、不校验归属（因核销由核销人员执行）。券码若可预测，等价于任意人可枚举并批量核销他人券。这是安全约束而非编码偏好。UUID4 被否是因为核销人员需人工读写券码，36 字符不可用。
- 关联：NFR-006、FR-014、FR-020

## ADR-011 口令用 hashlib.scrypt，不引入新依赖

- **决策**：`hashlib.scrypt(password, salt=16 字节随机, n=16384, r=8, p=1, dklen=32)`，盐与杂凑分列存储；校验用 `hmac.compare_digest`。
- **理由**：scrypt 是内存硬化 KDF，抗 GPU 暴破；且它在 Python 标准库中，**不增加任何安装失败点**。bcrypt 与 argon2 需要 C 扩展包，在不可控的演示机上是额外风险。
- **代价**：参数需手工选定而非由库自动升级；已把参数写入常量并注明，日后调参时旧杂凑仍可校验（杂凑串内含参数）。
- **明确排除**：明文、无盐杂凑、MD5/SHA1/裸 SHA256。这些不是"简化"，是缺陷。

## ADR-012 账号状态机与登录准入分离

- **决策**：`users.status ∈ {ACTIVE, PENDING, REJECTED}`。登录本身只校验凭证与"非 REJECTED"，**业务接口的准入另由依赖检查 `status == ACTIVE`**。
- **理由**：`PENDING` 用户必须能登录，否则无法查看自己的申请进度，只会反复提交注册造成垃圾数据。但它不能访问任何业务接口。把"能否登录"与"能否办业务"拆成两层，二者都简单；合成一层则必然出现"登录了却处处 403 且没有解释"的糟糕体验。
- **落地**：`get_current_user` 只拒 REJECTED；`require_roles` 额外要求 ACTIVE，并对 PENDING 返回专用错误码 `ACCOUNT_PENDING_APPROVAL`，前端据此跳转到审核进度页。

## ADR-013 券型建模：共用门槛，分化优惠计算

- **决策**：`campaigns.coupon_type ∈ {CASH, DISCOUNT}`。
  - 共用 `min_order_amount`（最低消费门槛，可为 0）
  - `CASH`：`face_value` 为减免额，必填且 > 0
  - `DISCOUNT`：`discount_percent`（1~99，表示折后百分比）与 `max_discount_amount`（封顶）必填，`face_value` 置空
- **数据库强制**：用两条 CHECK 表达"按券型必填"，而不是留给应用层判断：

  ```sql
  CHECK (coupon_type <> 'CASH' OR (face_value IS NOT NULL AND face_value > 0))
  CHECK (coupon_type <> 'DISCOUNT' OR (discount_percent IS NOT NULL
         AND discount_percent BETWEEN 1 AND 99 AND max_discount_amount IS NOT NULL))
  ```

- **`max_discount_amount` 为折扣券必填而非可选**：无上限的折扣券在大额订单上造成不可控的营销成本，这是真实业务的硬约束，不是防御性编程。
- **替代方案**：为两种券型分建两张表 —— 被否，它们的生命周期、库存、限领、核销逻辑完全相同，分表会把所有共用逻辑复制一遍。

## ADR-014 核销引入订单金额，但不改变幂等来源

- **决策**：`POST /api/redemptions` 新增必填 `order_amount`。核销流程变为：校验金额门槛 → 条件 UPDATE → 计算并落库实际优惠金额与核销门店。
- **理由**：引入券型后，没有订单金额就既无法判断门槛、也无法算折扣券的优惠额。这是券型的必然结果，不是额外复杂度。
- **幂等性不受影响**：幂等仍由券的状态机保证（ADR-004 不变）。门槛校验是**前置条件**，位于条件 UPDATE 之前；重复核销时条件 UPDATE 的 `rowcount=0`，走原有的回查判定，返回「已核销」。
- **判定顺序**：先看券状态（已核销/已过期），**再看金额门槛**。理由与 ADR-004 的终态优先一致 —— 一张已核销的券，即使这次的订单金额不达标，也应回「已核销」而非「未达门槛」，否则核销员会以为换个订单就能再用一次。
- **新增落库字段**：`user_coupons.order_amount`、`discount_amount`、`used_store_id`。前两者是核销时的事实快照，不可由现值重算（活动配置可能已改）；`used_store_id` 使管理员可按门店归集核销数据。

## ADR-015 门店为主数据，本期只读

- **决策**：`stores` 表由 seed 写入广州 11 个区的门店，本期不提供增删改接口。
- **理由**：门店主数据的维护（开店、闭店、迁址、编号规则）是独立的业务范围，牵扯审批与历史数据关联。本期需要门店只是为了让核销员归属与核销归集成立，做只读即可满足全部新增需求。
- **`stores` 与 `users` 的关系**：`users.store_id` 仅对 `VERIFIER` 有意义，用 CHECK 强制：非核销员不得关联门店，核销员必须关联门店。

# 设计变更 CR-002：管理员人员与业绩管理台

对应需求变更见 `req-plan.md` 的 CR-002。

## ADR-016 人员名册与下钻用聚合查询，不建汇总表

- **决策**：运营名册的「发布活动数／投放总量／已领取／已核销」与核销员名册的「累计核销」，均由 `campaigns` 与 `user_coupons` 实时聚合得出；下钻列表同样直查明细。
- **理由**：与 ADR-008 的统计口径决策一致。管理员后台是低频页面，人员规模在百量级，实时聚合的成本远低于维护汇总表的双写一致性风险。
- **实现方式**：名册用**单条查询加子查询聚合**，不在 Python 里循环查询。`list_verifiers` 已有的 `used_by` 分组子查询即为范式；运营名册需要按 `campaigns.created_by` 聚合两层（活动维度的库存之和、券维度的领取与核销数），用两个独立子查询各自 `GROUP BY` 后再 outerjoin，避免一次 join 造成的行放大重复计数。
- **明确排除**：为每个运营在 users 表上加 `campaign_count` 之类的派生列。它会与 `risk_blocked` 一样需要在写路径维护，而这里没有任何写路径需要它。

## ADR-017 下钻数据取核销快照，不取活动现值

- **决策**：核销记录列表的订单金额、优惠金额、券型描述，取 `user_coupons` 上落库的快照与核销时点的活动名，不用活动当前配置重算。
- **理由**：ADR-014 已确立快照的必要性。这里是它的第一个真正消费者 —— 若用现值重算，运营改一次活动配置，历史核销记录的金额就会集体漂移，管理员对不上账。
- **代价**：活动改名后，历史记录显示的是当前活动名（活动名未做快照）。这是刻意的取舍：金额是账，必须快照；名称是标识，跟随当前值更符合「这是哪个活动」的查询意图。

## ADR-018 名册与审核队列分成两个页面，不合并

- **决策**：「注册审核」只列 `PENDING`，「核销人员」「运营人员」列全部该角色账号（含 PENDING）。
- **理由**：两者的使用场景相反 —— 审核是待办清单，追求清空；名册是既成事实，追求可检索。合并后必然出现「已处理的要不要留在列表里」这种两难，且默认排序无法同时满足两边。
- **代价**：`PENDING` 账号同时出现在两处。这不是重复而是正确的：名册需要能看到「这个人还没审批」，否则管理员会疑惑名册里为何没有刚提交的人。

## 信息架构调整

侧栏分组「管理」改为「权限审批与管理」。分组下三项：注册审核、核销人员、运营人员。

理由：原分组名「管理」对管理员而言是同义反复（整个后台都是管理），改后的名称直接说明该组的两类职能 —— 审批权限、管理人员。

## 核销人员名册的姓名列

姓名列只呈现 `display_name`。原先在姓名下方以小字附 `username`，移除理由：管理员在名册上关心的是「谁」，账号名是登录凭证而非身份标识；两行结构还使行高翻倍，屏幕上能看到的人数减半。账号名移入下钻抽屉的人员信息区，需要时仍可查到。

# 设计变更 CR-002：运营增强闭环（2026-07-30）

需求来源：用户完成 45 项 `/grilling` 决策并明确确认。目标为演示型增强，核心规则真实生效。交付顺序：活动配置 → 多因素风控 → 运营驾驶舱。

## ADR-016 人工活动状态与时间状态正交

- `manual_state ∈ {RUNNING, PAUSED, TERMINATED}` 持久化；原 `PENDING/ACTIVE/ENDED` 仍由时间派生。
- 可领取要求 `manual_state=RUNNING` 且时间状态为 ACTIVE。
- 暂停可恢复，TERMINATED 不可逆；二者均不修改已发券的 `expires_at`。

## ADR-017 人群包保存标识、运行时统一求值

- 活动仅保存所选预设人群包，多个包按 OR 求值。
- 全局人群定义保存可调阈值；继承活动运行时读取当前全局值，覆盖活动保存自己的策略快照。
- 人群检查位于库存事务之前，避免非目标用户竞争库存行锁。

## ADR-018 每日额度与总库存共享同一领券事务

- 每日额度按 Asia/Shanghai 自然日统计成功券记录，不滚存，不建定时重置任务。
- 每日额度检查必须与库存扣减处于同一事务，并采用数据库可串行化的计数器/锁策略，防止并发突破额度。
- 多个领取时段存本地分钟区间，运行时把当前 UTC 转为 Asia/Shanghai 后判断。

## ADR-019 风控裁决确定性，AI 退出决策链

- 硬规则 + 因素加权产生唯一分数和三态结论；事件保存贡献明细、证据与策略快照。
- AI 只把既定事实组织为自然语言解释，不得回写分数或决策。
- 自动 BLOCK 立即标记为自动处置；只有 MANUAL_REVIEW 进入待办。
- 限制按用户与活动生效，支持 `restricted_until`，到期惰性失效。

## ADR-020 驾驶舱实时聚合并使用统一 as_of

- 不建预聚合表或缓存；总览、趋势、提醒和活动列表由实时 SQL 聚合。
- 一个驾驶舱响应使用同一 `as_of` 与筛选上下文，避免同屏数字漂移。
- 前端轮询可选 5/10/30 秒或关闭，不使用 WebSocket；未完成请求不叠加下一次轮询。
