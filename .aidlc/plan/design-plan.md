## ADR 技术决策记录

### ADR-001 并发控制完全下沉到数据库
- **背景**：库存不超发（INV-1）与每用户限领（FR-010）两个约束落在不同表上，跨表约束的并发正确性取决于数据库的隔离级别与锁原语。
- **决策**：库存用条件 UPDATE（`WHERE claimed_count < total_stock`）；个人上限用 `UNIQUE(campaign_id, user_id, seq)`。二者置于同一事务内，**应用层不实现任何锁、队列或串行化**。唯一冲突触发回滚，库存 `+1` 随事务一并回滚，不产生库存泄漏。
- **理由**：条件 UPDATE 的受影响行数即判定结果，无需 SELECT-then-UPDATE 的竞态窗口；唯一索引把"并发下两个请求算出同一个 seq"这一情形交给数据库拒绝。
- **代价**：单活动领取吞吐上限为 `campaign` 单行的更新速率（所有并发排在同一行的行锁上）。项目无 TPS 指标，已在 NFR-001 中接受。
- **替代方案**：Redis + Lua 原子扣减（被否，单机部署下多一个进程即多一个演示前置故障点，且 Redis 与 DB 的补偿逻辑是本项目性价比最低的复杂度）；悲观锁 `SELECT FOR UPDATE`（被否，等价于串行化但持锁时间更长）。
- 关联：NFR-001、FR-010、INV-1

### ADR-002 过期是时间的函数，不是状态
- **决策**：`user_coupon.status` 仅 `UNUSED` / `USED`；"已过期"由 `expires_at <= now()` 实时判断。活动的"未开始/进行中/已结束"同理由 `start_at` / `end_at` 派生，不落库。
- **理由**：过期若落库，要么引入定时任务扫表（单机部署下多一个调度器，且刷库之前的状态是错的），要么读时惰性回写（写放大）。不落库则任何时刻的查询都绝对准确。
- **代价**：统计 SQL 需写成 `status='UNUSED' AND expires_at <= now()` 这类条件，语句略长。
- 关联：INV-3、ADR-003、FR-003、FR-011、FR-030

### ADR-003 `expires_at` 落库，"是否过期"惰性判断
- **决策**：`expires_at = min(campaign.end_at, claimed_at + validity_minutes)`，在**领取时计算并落库**。
- **理由**：该值依赖领取时刻，无法事后重算；而"是否已过期"是对这个已知值的比较，必须实时。二者一个是数据、一个是判断，容易在实现时混淆，故单列一条 ADR。
- **附带收益**：`validity_minutes` 采用分钟粒度使"过期券核销"（SC-003）可在演示现场自然构造，无需改库或提前一天准备。
- 关联：D-16、FR-010、FR-020、NFR-010

### ADR-004 核销幂等由券的状态机承担
- **决策**：核销为单条条件 UPDATE；`rowcount = 0` 时回查券，**按 `status` 优先、时间其次**判定原因。不引入 `Idempotency-Key` 表。
- **理由**：券天生是单次消费资源，"是否已核销"这一事实存在于券自身。引入外部幂等键会派生"同一张券用两个不同 key 核销算不算重复"这类自找的问题，其答案最终仍要回到券的状态机。
- **终态优先**：已核销的券过期后再核销返回"已核销"。核销已发生且不可撤销；"过期"描述的是未被使用的券失去资格，对已消费的券不成立。返回"券已过期"会误导核销人员认为该券未被使用。
- 关联：NFR-002、FR-020、D-04

### ADR-005 AI 与交易链路解耦
- **决策**：推荐为独立只读接口，**不在领券路径上**；风控采用两层漏斗，规则层命中硬阈值直接拦截且**不调用 Bedrock**，仅灰区同步调用一次 AI。
- **理由**：领券是全系统唯一有并发正确性要求的接口。若挂上外部网络调用：响应时间受 Bedrock 支配；N+1 并发验收会变成 N+1 次并发 Bedrock 调用并触发限流，使"库存不足"与"AI 超时"两类失败无法区分；`campaign` 热点行的行锁被持有秒级。
- **附带收益**：SC-006（10 秒 50 次）由规则层拦截，全程零 Bedrock 调用，断网亦可演示。
- 关联：D-05、D-08、FR-050、NFR-003

### ADR-006 前端选 Ant Design 5，不用 Next.js
- **决策**：React 19 + Vite + TypeScript + Ant Design 5，单 SPA + 角色路由守卫。
- **理由**：前端是本项目最大成本项，需要五类页面（领券、我的券、核销台、活动管理与风险标记、统计面板）。Ant Design 自带 Table/Form/Statistic/Descriptions/Result 等成品组件，可避免手写表格与表单；shadcn/ui 需逐个复制组件并自行组合，前期速度更慢。SSR 在本项目无收益（无 SEO、无首屏指标），只增加"哪些代码跑在服务端"的心智负担与一个 Node 部署单元。
- **代价**：Ant Design 定制主题不如 Tailwind 灵活，产物体积较大。演示项目不受影响。
- 关联：CON-004、D-17

### ADR-007 人工审核的对象是风险标记，不是待批领取
- **决策**：风控判为"人工审核"时当次领取直接失败并写 `risk_event`；运营处理标记；解除后用户自行重领。**不创建 `PENDING_REVIEW` 券、不预占库存。**
- **理由**：依据需求原文"审核风控**标记**"。若预占库存，`claimed_count` 将可减，同时破坏 INV-1 与 INV-3，并使统计口径歧义化（被拒绝的那次算不算领过）；更严重的是给攻击者一个免费的库存占用手段——故意触发灰区判定即可让库存挂在审核中，**风控本身沦为拒绝服务工具**。
- **代价**：被判审核的用户需自行重领，而非被动等券到账。
- 关联：D-09、FR-052

### ADR-008 统计实时聚合，禁止预聚合表
- **决策**：全部指标由实时 SQL 聚合得出，不建汇总表、不加缓存层。
- **理由**：预聚合引入双写，双写必然出现不一致，届时面板数字与数据库打架是演示时最难解释的缺陷。项目数据量为演示级，实时聚合成本可忽略。
- **口径固定**：领取率分母为库存总量（系统无曝光埋点，CON-005）；核销率分母为已领取数。
- 关联：NFR-009、FR-030、INV-1、INV-2

### ADR-009 AI 输出不信任，服务端强校验
- **决策**：不依赖 Bedrock Structured Outputs 特性；prompt 内声明 JSON 结构，服务端对返回值无条件校验（字段齐全、活动 ID 必须落在本次候选白名单内、评分为 0~100 整数），任一不过即降级。
- **理由**：Structured Outputs 的模型与区域可用性无法在设计阶段查证（见 DQ-003），把 FR-040 的验收押在未验证的特性上是赌博；服务端校验是完全自主可控的。白名单校验同时消除"AI 推荐了不存在的活动"这一演示级风险。
- 关联：FR-040、FR-042、D-06、D-14

### ADR-010 券码不可预测
- **决策**：10 位 Crockford Base32（剔除 `0`/`O`、`1`/`I`/`L`），密码学安全随机源，唯一索引 + 冲突重试。
- **理由**：核销仅凭券码、不校验归属（因核销由核销人员执行）。券码若可预测，等价于任意人可枚举并批量核销他人券。这是安全约束而非编码偏好。UUID4 被否是因为核销人员需人工读写券码，36 字符不可用。
- 关联：NFR-006、FR-014、FR-020
